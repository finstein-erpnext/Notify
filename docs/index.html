Notify Documentation

Turn every Frappe bell notification into an Outlook-style desktop pop-up and a mobile lock-screen alert — powered by your own free Firebase project, with no external relay and no per-message cost.

🔔 Desktop & mobile 🔥 Firebase Cloud Messaging 🧩 Works with any Frappe app 🔒 Credentials stay on your site

Overview

Notify listens for anything that would appear in the Frappe bell (a mention, an assignment, a share, an approval, a workflow update) and delivers it in real time to the recipient's registered desktop browsers and phone. It runs on any Frappe site and works with any app — ERPNext, Frappe HR, LMS, or your own custom apps.

🖥️

Desktop pop-ups

A native OS notification with sound, even when the Frappe tab is minimised or in the background.

📱

Mobile alerts

Lock-screen push to employees' phones through the Frappe HR (ESS) app — no external relay server.

🎯

Targeted rules

Fan a document event out to everyone with access, or to specific roles, with optional Jinja templates.

🧾

Full audit log

Every send is recorded — who, what, and whether it was delivered, skipped, or failed.

How it works

Notify uses Firebase Cloud Messaging (FCM) — Google's free push service — to deliver messages to browsers and phones. You create your own free Firebase project, paste its credentials into Notify Settings once, and you are done. Delivery goes straight from your site to Google; there is no third-party relay in between.

There are two delivery paths, both handled in the background so a document save is never slowed down or broken by push delivery:

  • Bell mirror — every Notification Log the recipient receives is mirrored to their devices (when Push All Bell Notifications is on).
  • Fan-out rules — a Notify Rule watches a DocType for an event (new / update / submit / workflow state) and notifies everyone with access, or specific roles. See Notification Rules.

Installation

From your bench directory, fetch the app and install it on your site:

# 1. Download the app into the bench
bench get-app notify <your-repo-url>

# 2. Install it on your site
bench --site your-site.com install-app notify

# 3. Build assets & restart (production)
bench build --app notify
bench restart

The firebase-admin dependency installs with the app. If you ever need it explicitly:

./env/bin/pip install firebase-admin
✓

After installing, open Notify Settings and continue with Firebase setup. Nothing is sent until Notify is enabled and configured.

1 · Create a Firebase project

A one-time setup. Everything here is on Firebase's free plan.

Step 1 — Create the project

  1. Go to console.firebase.google.com and click Add project.
  2. Give it a name (e.g. My Company Notifications) and finish. You can skip Google Analytics.

Step 2 — Add a Web app (gives you the web config)

  1. On the project home, click the Web icon </>.
  2. Register the app with any nickname. You do not need Firebase Hosting.
  3. Firebase shows a firebaseConfig = { … } snippet. Keep this tab open — you will paste it in step 2.

Step 3 — Generate the VAPID key (Web Push certificate)

  1. Click the gear ⚙️ → Project settings → Cloud Messaging tab.
  2. Under Web configuration → Web Push certificates, click Generate key pair.
  3. Copy the key string it produces.

Step 4 — Download the Service Account (server key)

  1. Project settings → Service accounts tab.
  2. Click Generate new private key → Generate key. A .json file downloads.
  3. Keep this file safe — it is a secret.
🔒

The Web config values (Step 2) and VAPID key (Step 3) are public identifiers. The Service Account JSON (Step 4) is a secret — it stays only on your site and is never exposed to the browser.

2 · Configure Notify Settings

Open Notify Settings (type it in the Awesomebar / search).

  1. Enable Notify — leave ticked.
  2. Firebase Web Configuration — click the Paste firebaseConfig button, paste the firebaseConfig { … } snippet from Firebase Step 2, and click Fill Fields. This fills API Key, Auth Domain, Project ID, Messaging Sender ID and App ID automatically.
  3. VAPID Public Key — paste the key from Firebase Step 3.
  4. Service Account JSON — open the .json from Firebase Step 4 and paste its entire contents.
  5. Click Save.

A green “Push is configured and ready” banner confirms everything is valid. Use Send Test Notification to check (enable notifications in your browser first — see step 3).

💡

The full field-by-field reference for this screen is in DocType reference → Notify Settings.

3 · Turn on desktop notifications

Each user enables notifications once per browser:

  1. Open the Desk (/app). A blue banner appears at the top: “Turn on notifications…”.
  2. Click Enable Notifications.
  3. The browser asks for permission — click Allow.

From then on the device registers itself silently on every login and receives pop-ups automatically. Each different browser or computer needs its own one-time Allow.

⚠️

If a user previously blocked notifications the browser will not ask again. They must click the lock/tune icon in the address bar → Site settings → set Notifications to Allow, then reload.

To enable manually from the browser console: frappe.notify.enable() — see the Client JS API.

4 · Turn on mobile (ESS) notifications

Requires the Frappe HR app installed and the site on HTTPS. Notify makes the HR ESS mobile PWA work against your direct-FCM engine instead of an external relay, without modifying HRMS.

Administrator — once

  1. In Notify Settings, tick Enable Mobile / ESS Push.
  2. Set Public Site URL to the HTTPS address employees use (e.g. https://hr.company.com), or leave blank to auto-detect.
  3. Save. Notify keeps the HRMS relay flag and push_relay_server_url in sync for you.

Each employee — once, on their phone

  1. Open the HR app URL in the phone browser.
  2. Install it — Android (Chrome): menu → Add to Home screen; iPhone (Safari): Share → Add to Home Screen (required on iOS). Open it from the new icon.
  3. In the app: Profile → Settings → Enable Push Notifications → Allow.
📱

iPhone web push requires the app to be installed to the Home Screen (iOS 16.4+); it does not work in a plain Safari tab.

Everyday use

There is nothing to do day-to-day — Notify works in the background. A push is delivered whenever the recipient would get a bell notification, for example:

  • Someone @mentions you or assigns you a document
  • A document is shared with you
  • A workflow action needs your approval, or your request is approved / rejected
  • HR events (leave, expense, shift approvals) for ESS users

Click a pop-up (desktop or phone) to open the related document and act on it. To send yourself a test at any time, open Notify Settings → Send Test Notification.

Notification Rules

By default Push All Bell Notifications is on, so everything in the bell is delivered. Notify Rules let you push events that don't normally raise a bell notification — for example “notify all HR Managers whenever a Job Opening is submitted.”

Create a Notify Rule:

FieldWhat it does
Reference DocTypeThe DocType to watch, e.g. Job Opening.
Trigger EventOne of New Document, On Update, On Submit, or Workflow State Reached.
Workflow StateShown only for Workflow State Reached — notify only when the document enters this state (e.g. Pending CEO Approval).
NotifyAll Users With Access (everyone whose role can read the doctype) or Users With Specific Roles.
RolesShown for Specific Roles — the roles to notify.
Title / Body / Link templatesOptional Jinja templates to customise the message. Context: doc (the document), user.
Play SoundPlay a sound for this rule.

Every recipient is still checked individually for permission to the specific record — a rule never leaks a document to someone who can't read it. Only enabled rules that match are delivered.

Template example

# Title Template
New {{ doc.doctype }}: {{ doc.name }}
# Body Template
{{ doc.get("job_title") or doc.name }} needs your review.

Managing devices

Every browser or phone that enables notifications appears in Notify Device. You normally never touch this list — it fills and cleans itself:

  • Devices register automatically when a user allows notifications.
  • Tokens FCM reports as invalid are disabled automatically on the next send.
  • Devices unused beyond the Remove Inactive Devices window are cleared by a daily job.

Delivery log

Notify Log records every send for auditing and troubleshooting — the user, the content, how many devices were targeted, and the outcome:

StatusMeaning
QueuedAccepted and handed to the background job.
SentAt least one device accepted the message from FCM.
SkippedNot sent by design — no access to the referenced document, or quiet hours.
FailedNo device accepted the message (see Troubleshooting).

Hooks & architecture

For developers, here is how Notify wires into Frappe (from hooks.py):

# Desk client bundle (content-hashed, cache-busting)
app_include_js = "notify.bundle.js"

# Inject the public Firebase web config into bootinfo for logged-in users
extend_bootinfo = "notify.api.boot_firebase_config"

# Every bell notification becomes a push; rules fan out on document events
doc_events = {
    "Notification Log": {"after_insert": "notify.dispatcher.on_notification_log"},
    "PWA Notification": {"after_insert": "notify.dispatcher.on_pwa_notification"},
    "*": {
        "after_insert": "notify.dispatcher.on_document_event",
        "on_update":   "notify.dispatcher.on_document_event",
        "on_submit":   "notify.dispatcher.on_document_event",
    },
}

# Make the HRMS ESS PWA use our direct-FCM engine (no external relay)
override_whitelisted_methods = {
    "notification_relay.api.get_config":     "notify.api.relay_get_config",
    "frappe.push_notification.subscribe":    "notify.api.subscribe",
    "frappe.push_notification.unsubscribe":  "notify.api.unsubscribe",
}

# Daily cleanup of stale device tokens
scheduler_events = {"daily": ["notify.api.cleanup_stale_devices"]}

Module layout:

FileResponsibility
notify/dispatcher.pyTurns bell notifications & document events into pushes; applies rules, access checks and quiet hours; writes Notify Log. Heavy work runs in background jobs.
notify/push.pyDirect FCM sender via the firebase-admin SDK; caches the initialised app per service account; disables tokens FCM rejects.
notify/api.pyWhitelisted endpoints, boot config, and scheduled maintenance.
notify/service_worker.jsBackground FCM handler served at root scope; shows the OS toast and bridges every push to open pages.
notify/public/js/notify.bundle.jsDesk client: registers the SW, requests permission, registers the token, shows in-app toast + sound.

Scheduler & maintenance

Notify registers one daily scheduler job, notify.api.cleanup_stale_devices, which removes Notify Device rows whose last_seen is older than Remove Inactive Devices After (days) (default 60). No other background jobs run on a schedule; all push delivery is enqueued on demand and processed by the short queue.

Troubleshooting

The green “ready” banner doesn't appear

Make sure all Firebase web fields, the VAPID key, and the complete Service Account JSON are filled, then Save.

A user sees no “Enable” banner

They have already granted permission (nothing to do), or the site isn't on HTTPS. Push requires HTTPS (or localhost).

Notifications were blocked by the user

Browsers won't re-ask once blocked. Click the lock/tune icon in the address bar → Site settings → set Notifications to Allow → reload.

Everything is “ready” but pop-ups don't arrive (desktop)

The most common cause on corporate networks is a firewall blocking Google's push connection. FCM uses a persistent connection to Google on ports 5228–5230. Open chrome://gcm-internals/ and check Connection State — if it isn't Connected, the network is blocking it.

🌐

Ask IT to allow outbound to mtalk.google.com on ports 5228–5230 (plus 443), or test on a phone hotspot to confirm.

Phone gets nothing

  • iPhone: the app must be installed to the Home Screen (iOS 16.4+); web push doesn't work in a plain Safari tab.
  • Check the phone allows notifications for the app and isn't in Do Not Disturb.
  • On office Wi-Fi the same port-5228 block applies; phones usually work on mobile data.

No sound

Ensure Play Sound is on. A custom sound plays for the desktop pop-up while the tab is in front; background and mobile alerts use the device's own notification sound (a browser/OS rule).

FAQ

Do I have to register each user's device manually?

No. Users allow notifications once per browser/phone; devices register themselves automatically after that.

Can I enable notifications for everyone by default?

Browsers require each user to allow once — it can't be pre-granted, except by an IT-managed browser policy (Chrome Enterprise / MDM) that auto-allows your site's URL.

Does it cost anything?

No. It uses your own free Firebase project and sends directly — no relay, no per-message fee.

Which apps does it work with?

Any Frappe app, because it hooks into the standard bell (Notification Log) — ERPNext, HR, LMS, and custom apps.

Is my data sent anywhere?

Credentials stay on your site. Delivery goes through your own Firebase project (Google), like any push notification.

Limits & notes

  • Desktop pop-ups appear while the browser is running (the tab may be closed/minimised). A pop-up with no browser open at all needs a native desktop app and is out of scope.
  • iPhone web push requires the app installed to the Home Screen (iOS 16.4+).
  • Custom sound applies to the desktop foreground pop-up; background and mobile alerts use the device's default notification sound.
  • HTTPS is required for push on real devices; localhost works for local testing.
  • Networks that block Google's push ports (5228–5230) will prevent delivery on that network.
